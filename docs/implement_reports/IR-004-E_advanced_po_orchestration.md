# [IR-004-E] PO 에이전트 고도화: 의도 분류 및 워크플로우 최적화

**날짜**: 2026-04-12  
**단계**: Phase 5 보완 — 오케스트레이션 지능화 및 사용자 경험 개선

---

## 구현 배경

기존 에이전트 워크플로우는 모든 사용자 입력을 '개발 태스크'로 치부하여 단순 질문이나 분석 요청 시에도 불필요한 태스크 생성과 QA 검증 루프를 강제하는 경향이 있었습니다. 이로 인해 '분석 실패 → QA 거절 → 무한 루프'가 발생하는 UX 저해 요인을 발견했습니다.

---

## 구현 내용

### 1. PO 의도 분류(Intent Classification) 도입 (`po.py`)
- **의도 구분**: 사용자의 입력을 `INQUIRY`(조회/분석), `IMPLEMENTATION`(구현/수정), `CONVERSATION`(단순 대화) 세 가지 유형으로 분류하도록 PO의 의사결정 구조를 개선했습니다.
- **맞춤형 전략**:
  - `INQUIRY`: 제품 설계자(SA)에게 분석을 맡기되, 결과가 만족스러우면 QA를 거치지 않고 직접 답변 후 종료할 수 있도록 지시.
  - `IMPLEMENTATION`: 기존과 동일하게 하위 에이전트 간의 엄격한 협업 루프(SA -> CD -> QA) 가동.
  - `CONVERSATION`: 다른 에이전트 호출 없이 PO가 직접 답변 후 즉시 종료.

### 2. QA 에이전트의 검증 유연성 확보 (`qa.py`)
- **검증 기준 다변화**: QA 에이전트가 "배포 가능 여부"만 따지던 것에서 벗어나, 분석 요청(Inquiry)의 경우 "제공된 설명이 충분하고 논리적인가"를 검증 기준으로 삼도록 시스템 프롬프트를 수정했습니다.
- **루프 제어**: 무조건적인 Rejection보다는 PO의 의도를 파악하여 적절한 피드백을 주도록 가이드를 강화했습니다.

### 3. 사용자 경험 개선
- **`response_to_user` 필드 활용**: PO가 자신의 오케스트레이션 전략(예: "분석을 위해 설계자를 호출하겠습니다")을 사용자에게 미리 설명하여 투명성을 높였습니다.

---

## 검증 결과

- **분석 요청 테스트**: "폴더 내용을 알려줘"와 같은 질문 시, PO가 이를 `INQUIRY`로 판단하고 불필요한 코드 수정 태스크 없이 분석 결과만 깔끔하게 전달하는 것을 확인.
- **무한 루프 방지**: 분석 실패 시 QA가 무조건 거절하기보다 PO에게 보완을 요청하거나, PO가 직접 상황을 설명하고 종료하는 유연한 흐름 확인.
